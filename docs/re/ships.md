# Computer ships: roster, entry, pictures and perspective shifting

Which ships a wave holds, how the set-up picks and builds them, how they come in, what they look like and what the 'P' key does. The pilot, the tick's ship calls, the laws and the arrest are in [pilots.md](pilots.md); contact, damage, death and capture are in [ship-contact.md](ship-contact.md). [DESIGN]

Notation as in [core.md](core.md): ship-record fields `+0xNN` relative to DGROUP:0x7090 + 0x15a·i; design words DGROUP:0x96xx + 0xad·n relative to the design record of `design_index` (+0x4e) n; `r.+NN` a 0x7c-byte roster record at far DGROUP:0x6e24 + 0x7c·r ([formats.md](formats.md#ship-roster-records-0x7c-bytes)); `shp.+NN` a MASTER.SHP record (0x41 bytes at far DGROUP:0x6e20); `bod.+NN` a MASTER.BOD record (0x2c bytes at far DGROUP:0x6e1c). Arithmetic is 16-bit signed unless marked; `cdq`/`cwde` in the listings are `cwd`/`cbw` ([pitfalls.md](pitfalls.md)). `rand()` is seg5:0xdc. Calls are written in declaration order; every routine here is cdecl (`retf`) unless named Pascal.

Teams (SHP +0x03, 0-based, INSPACE.INI `[Teams]` Team1 … Team8): 0 AVENGERS, 1 PREDATORS, 2 FUZZY ONES, 3 PIRATES, 4 KNIGHTS, 5 SPEED DEMONS, 6 RENEGADES, 7 ENFORCERS [BYTES INSPACE.INI] [BYTES MASTER.SHP]. The six team-7 ships and their SHP +0x05 ("attitude to enemies", which for an Enforcer is its class): INTERCEPTOR (22) 1, CONSTABLE (35) 3, LETHAL WEAPON (42) 1, PATROLMAN (47) 2, TERMINATOR (77) 0, ELIMINATOR (85) 0 [BYTES MASTER.SHP]. That matches the manual's three classes: Patrol (Patrolman, Constable), Intercept (Interceptor, Lethal Weapon), Terminator (Terminator, Eliminator) [MANUAL Laws of Inner Space].

## Summary
- **The design team word** DGROUP:0x970a + 0xad·n has four writers; the one every placement runs is seg14:0x14ca inside seg14:0x1430(i). Without it every team test reads 0 and no team-7 branch runs.
- **The roster builder** seg14:0x0(mode) picks the wave's ships in a fixed order: the player, the directory's known ships (revisited directory only), the teammates (count DGROUP:0x9336), the other teams' ships up to the target count DGROUP:0x9338, then at most one Terminator (two with a high difficulty), one Patrol officer and, on a call-in only, one Interceptor; at most 8. Each non-Enforcer ship is either a known roster record (seg14:0x3274's best score) or a new record for the best MASTER.SHP design (seg14:0x2300's best score), whichever scores higher (seg14:0xdd6). Enforcers get no roster record: their SHP index lives in the word table DGROUP:0x4ed8 indexed by ship byte +0x5e.
- **The counts** come from the wave generator seg9:0x3202 (DGROUP:0x9336, DGROUP:0x9338, the avenger list DGROUP:0x4f1c with its count DGROUP:0x994) and from seg9:0x2828 (DGROUP:0x932c, the Patrol flag). Wave 1 has no other ship; wave 2 has one teammate.
- **Entry** of a wave's ships is in [world.md](world.md#ship-entry-seg70x1d0c): the computer ships wait off-world in `state` 100 and enter one every 5000 ms through a random gate. Interceptors (team 7, +0x5e = 1) never enter that way. Mid-wave arrivals go through seg13:0xadbe, the call-in.
- **Pictures:** every ship i has its own sheet in image slot 0x28 + i, built by the same seg14:0x11a8(i) as the player's.
- **Perspective shifting** is WM_KEYUP 'P': the next live ship of the player's team becomes the player's ship and the view pans to it.

## The design team word
Design record field +0x38 ([structs.md](structs.md#design-records)) has exactly four store sites in INSPACE.EXE [BYTES seg14:0x3e9 seg14:0x47e seg14:0x14ca seg9:0xdbf]:


| Site | When | Value |
|---|---|---|
| seg14:0x3e9 | seg14:0x0's fresh roster (DGROUP:0x91f8 ≤ 1 in the placement), design 0 | sext(shp.+0x03) of the player's MainShip pick; its low byte also goes to r.+0x64 (seg14:0x3f3) |
| seg14:0x47e | seg14:0x0 in later waves, the player's design (ship 0 +0x4e) | sext(r.+0x64) of record DGROUP:0x931c |
| seg14:0x14ca | seg14:0x1430(i), every placement, every ship, before seg14:0x1b84 | R = ship +0xd6 ≠ −1: sext(r[R].+0x64) (seg14:0x14ad); R = −1: sext(shp[s].+0x03) with s the SHP index of the ship (seg14:0x14c0) |
| seg9:0xdbf | the GAME OVER entry seg9:0xd6c | 0 for designs 0 … 9, with design word +0x4e (DGROUP:0x9720) |

- s is r[R].+0x00 for R ≠ −1, else the word DGROUP:0x4ed8 + 2·sext(ship byte +0x5e) (seg14:0x1461-0x146a); s > DGROUP:0x95aa − 1 (signed) makes r[R].+0x00 = 0 and s = 0 (seg14:0x1471-0x148e). With R = −1 that store lands 0x7c bytes before the roster block (far DGROUP:0x6e24 − 0x7c); it cannot happen with the SHP indices seg14:0x2300 returns (0 … count − 1, or 1) [BYTES seg14:0x1444-0x148e seg14:0x317f-0x3190].
- r.+0x64 comes from shp.+0x03 when a record is made (seg14:0x3f3, seg14:0xdd6 at seg14:0x1087-0x109f) and the save reader turns 7 into 0 (formats.md "Reading" step 8). No Enforcer is ever given a roster record ('The wave's ships'), so team 7 reaches the word only through seg14:0x14c0, from MASTER.SHP.
- **Precision.** Before the store, an SHP index above DGROUP:0x95aa − 1 is reset to 0, and so is roster word +0x00 of the record; for an Enforcer slot that store goes 0x7c bytes before the roster block. No caller reaches it with the SHP indices seg14:0x2300 returns (0 … count − 1, or 1). With argument −1, seg14:0x0 calls seg14:0x1430(k) for every slot k below the slot counter (seg14:0xb3e); with any other argument only for the new last ship DGROUP:0x9316 (seg14:0xb73). The stores to design word +0x38 have no other writer: a search of every `0x970a` and `[reg − 0x68f6]` operand and of the absolute addresses of designs 1 … 9 (DGROUP:0x97b7 … 0x9d1f) finds seg14:0x3e9, seg14:0x47e, seg14:0x14ca and seg9:0xdbf, and no block copy covers a design record. The GAME OVER entry seg9:0xd6c zeroes words +0x38 and +0x4e (DGROUP:0x9720) of designs 0 … 9 (seg9:0xdb4-0xdca). [BYTES seg14:0x1471-0x148e seg14:0xb3e seg14:0xb73 seg9:0xdb4-0xdca]

## Ship records and objects of computer ships
- Ship i is pool DGROUP:0x9324 (14) record i (0x70 bytes, far DGROUP:0x1e30 for pool 14) and ship record i (0x15a bytes at DGROUP:0x7090 + 0x15a·i), i = 0 … DGROUP:0x9316 ≤ 7 (structs.md "Ship records"). seg14:0x0 sets DGROUP:0x9316 = n − 1 and both pool counts to n, and resizes the pool block to max(n, 1)·0x70 [BYTES seg14:0xa1f-0xa84].
- seg14:0x1430(i) also writes, for every ship: ship word +0x04 = i + 0x28 (seg14:0x152d), the activity words +0x52 = 0 (7 for the player with `PlayMode` ≠ 0) and, for a team-7 design with sext(+0x5e) > 1 (the Patrol class), +0x52 = 0x14, +0x54 = DGROUP:0x9324, +0x56 = DGROUP:0x9646 [BYTES seg14:0x161c-0x1667]. In a kind-7 wave every ship but the player (or every ship in the demo) gets dword +0x52 = 0x000e0004 (+0x52 = 4, +0x54 = 14), +0x56 = the player (1 for the player itself), seg3:0xf4(i, 14, that) and +0x58 = i [BYTES seg14:0x166b-0x16bd] (M6).
- **No-roster path** (R = −1, seg14:0x1a5d-0x1b78): weapons +0xcb = 3, slot 1 = weapon 15 (HANDCUFFS) with count 1, slot 2 = shp.+0x06 with count 20 (slot 0 = weapon 0, count 1, from seg14:0x1531/0x1536); for sext(+0x5e) = 0 (the Terminator class) +0x52 = 0x17, +0x54 = DGROUP:0x9324, +0x56 = seg14:0x4520(DGROUP:0x9346, DGROUP:0x9316) and byte +0xcd = its low byte, both replaced by the player when the result is negative, then byte +0xed = 1; systems 100; bytes +0xee + k and words +0x72 + 2k = 0 for k < 5 (not k ≤ DGROUP:0x9316); `fuel` = 40·sext(shp.+0x00); +0xac = +0xad = 1; +0x24 = +0x0a = 2; `resources` = 100; `credit` = 0; +0x82 = 0; words +0x62 + 2j = 0 for j < DGROUP:0x9316 [BYTES seg14:0x1a62-0x1b69].
- seg14:0x4520(r, last) returns the first ship j = 0 … last whose +0xd6 = r, or −1 [BYTES seg14:0x4520-0x455b]. DGROUP:0x9346 is the arrest warrant: seg9:0x2828 sets it to the player's +0xd6 when a live team-7 ship with +0x5e = 0 holds (+0x54, +0x56) = (14, player) at the wave end (world.md "Order" DGROUP:0x9346), so a Terminator placed by the next wave's seg14:0x0 hunts the ship that carries that roster index, the player after a perspective shift included.
- Fields a call-in writes (seg13:0xae68, "Mid-wave arrivals"): +0x52 (activity), +0x54 = 14, +0x56 = the target ship, +0x32 = 14 and +0x34 = the target (`goal_pool`, `goal_rec`), dword +0x94 = now, byte +0xed = 1, +0x58 = the ship's own index, dword +0x98 = now + 5000, +0x38 = 3, byte +0xcd = the target's low byte [BYTES seg13:0xb1a0-0xb1e3 seg13:0xb5fd-0xb644 seg13:0xb6c1-0xb6d8]. [structs.md](structs.md#ship-records-8--0x15a-bytes-at-dgroup0x7090) lists +0x52 … +0x58, +0x98, +0xcd and +0xed as the pilot's order words ([pilots.md](pilots.md)); here they are only set.

### Further effects of seg14:0x0
- DGROUP:0x95b6 = the argument; DGROUP:0x4ed8 … 0x4ede = 0; the per-slot build flags [bp−0x54 + 2k] = 1 for k < 8. Kinds 6 and 7: DGROUP:0x932c = 0 and DGROUP:0x9346 = −1 [BYTES seg14:0x65-0x8e seg14:0xdd-0xf1].
- **Head, precisely.** When DGROUP:0x95a8 ≠ 0 outside kinds 6 and 7, the demo player's death (seg16:0xaea sets the word) first raises DGROUP:0x9336 to at least 1 and clamps DGROUP:0x9338 to 1 … 7, then clears DGROUP:0x95a8; only after that DGROUP:0x9338 = min(7 − DGROUP:0x932c, DGROUP:0x9338) runs, signed [BYTES seg14:0x10-0x4c seg14:0x52-0x62]. The Detail adjustment belongs to the DGROUP:0x9338 > 2 branch: a value of 2 or less skips the cap Detail + 3, and DGROUP:0x9334 grows only on the decrement path and only when it is above 0 (signed) [BYTES seg14:0x83-0xca]. Every argument other than −1 jumps from seg14:0xfb to seg14:0x5dd; only the −1 path zeroes the slot counter, so an argument below −1 would read it uninitialised and no caller passes one [BYTES seg14:0xcd-0xda seg14:0x1be].
- **Wave > 1 with argument −1:** every roster record r ≤ DGROUP:0x931a decays its bytes +0x3c + j (j ≤ DGROUP:0x931a) to ((10b − T)·9/10 + T)/10 with T = word DGROUP:0x3824 + 18·sext(+0x64), the diagonal entry relation[team][team] of the 8 × 8 word table, in 16-bit signed divisions [BYTES seg14:0x104-0x183].
- **Wave 1** creates the player's record: seg14:0x2300(0, 0), then GlobalAlloc(0x42, 0x7c), returning at once on failure, and DGROUP:0x931a = 0. Record 0 gets +0x3c … +0x63 = 0, +0x38 … +0x3b = 100, the five-entry table cleared, the weapon +0x29 (remapped through DGROUP:0x2f8a when DGROUP:0x11aa = 0) with +0x1d = 2 and +0x1f = 20 (or +0x1d = 1 when it has none), +0x06 = 0, +0x72 … +0x75 = 1, +0x1c = SHP +0, word +0x02 = 15, +0x04 = 0 and +0x64 = the team, with design 0 word +0x38 set to the same team. Bytes DGROUP:0xa14d … 0xa160 are zeroed, seg9:0x5be0(0, 0) names the record, and DGROUP:0x9646 = ship 0 +0xd6 = +0x4e = DGROUP:0x1318 = 0. In a later wave ship 0 takes the player's design index and DGROUP:0x931c, DGROUP:0x9646 = 0, and slot 0's build flag is cleared when DGROUP:0x92e4 = 0 [BYTES seg14:0x23b-0x438 seg14:0x43a-0x47e].
- Each known ship also marks the avenger entries DGROUP:0x4f1c + 2j (j < DGROUP:0x994) as −120 when the entry equals its roster index, equals −team, or is +100 with team 3 (seg14:0x2300 tests −100 for the Pirates); with DGROUP:0x92e4 = 0 its build flag is cleared (seg14:0x52c), and the second loop of the tail sets it again [BYTES seg14:0x55b-0x5ae seg14:0x58e seg14:0x52c].
- **Adjustments of DGROUP:0x9338 that follow the known ships.** (a) When ([bp−0x2a] = 0 and DGROUP:0x9336 ≠ 0) or DGROUP:0x932c ≠ 0, with argument −1, outside kinds 6/7 and Demon's Gate: DGROUP:0x9338 = min(max(slot, DGROUP:0x9338), 7); this lifts the wave-1 value 0 back to 1 [BYTES seg14:0x5dd-0x623]. - **Other-team loop.** It runs for argument −1, or an argument other than the player's design team and at most 6, and has no slot cap [BYTES seg14:0x723-0x740]. With an argument other than −1 the teammate loop did not run in the same call, so [bp−0xa0] is never written (uninitialised, not only stale); DGROUP:0x95b2, which seg14:0xdd6 compares with DGROUP:0x95b4, is the last seg14:0x3274 result, or −3000 (kind 0x13), or −10000 (race).
