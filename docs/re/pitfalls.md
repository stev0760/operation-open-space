# RE pitfalls

These are rules for working on this binary. Each one exists because ignoring it has produced a wrong conclusion. Check this list before proposing a new extraction method.

## Packing and relocations
- **Packed segment layout:** `[word reloc count][compressed bitstream][relocation table]`. The bitstream starts at `fo+2`, and bit `1` means a literal. Settle decompressor parameters empirically against the golden hashes (`re/tests/test_unpack.py`), never by reading the loader. `[BYTES INSPACE.EXE segment table]`
- **The NE header's relocation counts are zeroed.** The real relocations sit inside each packed segment. `[BYTES INSPACE.EXE segment table]`
- **Relocation chains:** they can reach 159 sites, so never cap a chain walk. Special-base records chain through the segment word as well as import records: `seg4:0x24` → `seg4:0x6b` → `0xFFFF`. A `9a .. .. ff ff` call is the tail of such a chain, not a broken call. `[BYTES seg4:0x68]`
- **In a special-base far call (`9a oo oo ss ss`) the relocation site is the segment word.** The offset word holds the real target offset; only the segment words carry chain links. Taking chain heads alone finds 122 of the 553 internal far-call targets. `[BYTES seg4:0x24]`
- **seg1 of `INSPACE.EXE` is the OptLoader stub** (code, flags `0xd50`, 2,164 bytes). It is not DGROUP. **DGROUP is seg19** (NE autodata). Initialised data ends at `DGROUP:0x17b5`; everything above that is BSS filled at runtime. Tables that live in BSS can't be read from the file. `[BYTES INSPACE.EXE segment table]`
- **seg5 is the Borland runtime library** and starts with normal Borland startup at `seg5:0x1a` (`xor bp,bp; push bp; call KERNEL.InitTask`). Its assembly routines lack standard prologues, so prologue scans miss them. Disassembling the compressed bytes produces a fake "stub overwrote seg5" story. `[BYTES seg5:0x1a]`
- **Decode packed code up to minalloc, not the decompressed length.** OptLoader zero-fills the rest, and code can rely on it: the final `retf 0xa` of seg4 in the game's FACTORY.EXE needs the zero-fill byte, and `theworks/FACTORY.EXE` repeats the pattern at seg4:0x634f. `[BYTES FACTORY.EXE seg4:0x5d0f]`
- **Segment preloading:** segments 9–18 are not PRELOAD (flags `0x1c18`). Don't assume all segments preload. `[BYTES INSPACE.EXE segment table]`

## Reading code
- **Win16 KERNEL/USER/GDI APIs use the Pascal convention.** Arguments are pushed left to right, so the first `push` is the first argument. Borland's own C functions are cdecl (right to left). Check the callee's module before assigning roles to pushed operands. `[REF Win16 SDK]` `[REF Wine 11.0 *.spec]`
- **Some DOS call numbers arrive in registers.** The Borland directory-search helpers load the function number into `AL` and share a tail that issues `mov %al,%ah` and DOS3Call: `seg5:0x352` is findnext (`mov $0x4f,%al`), `seg5:0x364` is findfirst (`mov $0x4e,%al`). So a search for `mov $0x4e00,%ax` immediates finds nothing even though the game enumerates directories. `[BYTES seg5:0x35d]` `[BYTES seg5:0x36f]` `[BYTES DGROUP:0x1260]` (`C:\*.*`)
- **KERNEL.1 FatalExit does not return; KERNEL.137 FatalAppExit can.** A decoder that falls through after FatalExit swallows the next prologue: the call at `seg5:0xb9e` is followed by one pad byte and then the function at `seg5:0xba4`. The runtime library expects FatalAppExit to return: the instructions after its call at `seg5:0xb95` set up `FatalExit(0xff)` as a fallback and nothing else reaches them. `[BYTES seg5:0xb9e]` `[BYTES seg5:0xb95]`
- **Stack locals are not struct fields.** Indices loaded from `-0xc(%bp)` or `-0xa(%bp)` are locals (loop counters, for example). Before naming a field, trace where the base and index registers come from. `[BYTES seg4:0x1003]`
- **Check each struct field against the stride.** An offset at or beyond the stride (for example `+0x74` in a `0x70`-stride struct) belongs to something else. A ship-record field is its address minus DGROUP:0x7090: `[bx + 0x7134]` with bx = 0x15a·k is field +0xa4, not +0x144. `[DESIGN]` `[BYTES seg8:0x60d9 seg8:0x60fe]`
- **DGROUP:0x9684 is the player's race place, not a game mode.** seg4:0x8b82 sets it to 1 and adds 1 for each ship ahead, so the comparisons with 1 and 2 test first and second place. The screen state is DGROUP:0x90f4 ([globals.md](globals.md#game-state-globals)). `[BYTES seg4:0x8bda]` `[BYTES seg4:0x8c0d]`
- **A string load can be dead code.** The branch at seg3:0x16a loads "NO TARGETS" and "AVAILABLE", but no path reaches it: pool −1 fails both checks before it, and seg3:0xf4 jumps past it. Confirm that a path reaches a string load before specifying the message from it ([structs.md](structs.md#ship-records-8--0x15a-bytes-at-dgroup0x7090)). `[BYTES seg3:0x149]` `[BYTES seg3:0x14d]` `[BYTES ENG_LANG.DLL STRING 138]` ids 2205–2206
- **Win16 `ExtractIcon(hInst, path, -1)` returns the number of icons** in the file, not an icon. `[REF Win16 SDK]`
- **Packed-file offsets are not addresses.** A string's offset in the packed `INSPACE.EXE` (for example the "Unregistered Copy" text) is a file position inside a resource, and code never references it. Convert addresses with `isre addr`. `[BYTES INSPACE.EXE 5000 143]`
- **Byte 0x99 in 16-bit code is CWD.** The listings print it as `cdq`, but in a 16-bit segment it only sign-extends AX into DX. Ordinal 14's `imul`, `cwd`, `idiv 100` therefore drops the high word of the product and wraps ([shell.md](shell.md#palette)). Every `cdq; idiv r16` of a listing is a 16-bit signed divide of sext(AX), as in the gun's velocity and slot tests and the retarget's 2/3. `[BYTES ISPACE.DLL seg5:0x518c]` `[BYTES seg11:0x51cf seg11:0x5031 seg11:0x5529 seg12:0x60a]`
- **Calls are written in declaration order.** A Pascal callee (`retf n`) takes its first declared argument from the first push, at the highest stack offset, so [bp+6] holds its last argument; a cdecl callee (`retf`) takes its first argument from the last push, at [bp+6]. The docs write every call in declaration order: seg8:0xb76(pool·256 + rec, kind, srcDC, masked) has the masked flag at [bp+6], and the shot update seg8:0x3aec(j, i) has the sub-step i at [bp+6] and the slot j at [bp+8]. Reading the pushes from [bp+6] up gives the reverse order for a Pascal callee; check the `retf` before naming the arguments. seg8:0x1290 (`retf 8`) gets the target's mass as its first push and 25 as its last, so seg8:0x5ab0 calls seg8:0x1290(mass, 25); seg13:0x2e60 (`retf 6`) gets the pushes j, cr, 4 and is seg13:0x2e60(j, cr, 4). `[BYTES seg8:0xb76 seg12:0x2f9 seg12:0x313 seg8:0x3aec seg7:0x946 seg8:0x5db5 seg8:0x5dbe seg8:0x5dc0 seg8:0x131c seg13:0x2f2c]` `[REF Win16 SDK]`
- **A leftover argument can be a callee's argument.** seg8:0x29ea is `retf 6`, so a word pushed before its second call stays on the stack and is the next call's extra argument: seg11:0xa4a6's fifth argument, the source pool, is that word. Count each callee's `retf n` and `add sp, n` before assigning the pushes. [BYTES seg8:0x29ea seg11:0xa33b-0xa374]
- **A division by the wrong quantity is still the original's.** seg8:0x348e adds lo16((S·n)/ex) to the x velocity, dividing by the x distance and not by the length n, and adds it to the target's velocity, not the record's. A port keeps the arithmetic and guards the zero divisor ([ADR 0016](../decisions/0016-undefined-reads.md)). [BYTES seg8:0x356c-0x35c3]
- **"Kind" names two words of a weapon record.** W+0x0a (DGROUP:0x2f5e) is the launch kind, W+0x24 (DGROUP:0x2f78) the end kind; the mover and dispatcher text of core.md calls the second the weapon kind in places. Read the offset, not the noun. [BYTES seg11:0xad10 seg12:0x452]
- **Message 0x401 depends on the control class.** Sent to an edit control it is EM_SETSEL (EM_LIMITTEXT is 0x415); only for a combo box is it CB_LIMITTEXT. Check the class of the target window before naming a WM_USER-based message. `[BYTES ISPACE.DLL seg10:0x134 seg10:0xd83]` `[REF Win16 SDK windows.h]`
- **A DGROUP word that is zero in the file and has no writer is a build constant.** Branches gated on it are dead in this build: DGROUP:0x5d0, DGROUP:0x1120 and DGROUP:0x1122 disable the CD-edition branches of seg10:0x885e. List the writers before treating a branch as live. `[BYTES seg10:0x8959 seg10:0x89b1 seg10:0x89c7]`
- **A "Compressed" label is not compressed data.** The Options dialog shows "Compressed" for an FX DLL only when that DLL carries string 2314, and ISPACE.DLL decompresses nothing: every shipped WAV is plain 8-bit PCM ([sound.md](sound.md#slots)). `[BYTES ISPACE.DLL seg9:0x1b55 seg9:0x1b71]` `[BYTES SND_FX.DLL 100]`
- **Under Wine, GetWinFlags reports WF_WINNT.** Code that branches on it, such as the media-ID serial read in ISPACE.DLL seg10:0x4440, takes its Windows NT path in every oracle run, so the oracle never shows the Windows 3.x and 9x path. `[BYTES ISPACE.DLL seg10:0x4452 seg10:0x4457]` `[ORACLE install-0001]`
- **seg8:0x3aec is the gun's shot-slot update, not the world update.** The loop that opens each wave frame (25 or 45 calls, [world.md](world.md#update-loop) step 6) moves the gun's shots in the slots at DGROUP:0x6098 ([core.md](core.md#shot-update-seg80x3aec)); the pool objects move later, through the movers that call the integrator seg8:0x1b54 ([world.md](world.md#update-loop)). `[BYTES seg7:0x942 seg8:0x3afb seg8:0x1b54]`
- **Key messages are handled synchronously, not through a next-pass mailbox.** WndProc stores the message in DGROUP:0x8e62 and calls the game pass seg2:0x1c08 at once, which hands it to the input router in the same call; seg7:0x863 delivers only a message still left over ([world.md](world.md#router)). `[BYTES seg2:0x783 seg2:0x799 seg7:0x50e seg7:0x863]`
- **Check ES before naming a +0x28 store.** seg14:0x170a stores to byte +0x28 + i of a 0x7c-byte roster record (ES from DGROUP:0x6e26), not to the ship's heading word +0x28; the ship set-up writes the heading only at seg14:0x15fa. `[BYTES seg14:0x170a seg14:0x1742 seg14:0x15fa]` The same holds for other offsets: seg9:0x60bc's off-world vx = 0 and vy = −30 go through the pool-14 pointer DGROUP:0x1e30 to object words +0x0c and +0x0e, not to the ship record's thrust and drag words of the same offsets. `[BYTES seg9:0x6343 seg9:0x638a seg9:0x6394]`
- **The help page's TURN RATE is not the turn rate.** It prints 1350/r from the turn word r, but the turn cadence adds r to an accumulator that must fall below 10, which gives 1350/(r + 10) RPM; take rates from seg13:0x616, not from the help text ([world.md](world.md#turning)). `[BYTES seg17:0x3771 seg13:0x616]`
- **seg8:0x285a measures in 1/8-unit cells.** It shifts both points right by 3 and wraps at 3200, so the hazard thresholds 150 and 80 are 1200 and 640 world units. `[BYTES seg8:0x285a seg9:0x10d4]`
- **The sine bytes at DGROUP:0xf00 are not round(sin·128).** 57 of the 91 entries differ, so copy the bytes instead of computing them ([world.md](world.md#helpers)). `[BYTES DGROUP:0xf00]`
- **A ship's mass changes during the wave.** The set-up stores the design mass in object +0x44, but seg11:0x1bcc rewrites it every 1000 ms as design mass + fuel / 20; reading only the set-up misses the fuel term. `[BYTES seg14:0x20bc seg11:0x1cfe seg11:0x1d26]`
- **The mode-1 flame length has no value in the original.** In mode 1 seg11:0x63b4 skips seg11:0x65e7's velocity change and stores object byte +0x2f from the stack words [bp − 0x14] and [bp − 0x10], which only the skipped branch writes, so +0x2f is whatever an earlier call left there ([world.md](world.md#thrust)). Do not read a rule out of a trace of that byte; the port's value is a [DESIGN] choice, and the visible flame does not depend on it, because the flame paste seg11:0xb09c never reads +0x2f. `[BYTES seg11:0x65e7 seg11:0x6617 seg11:0x66a9 seg11:0x684a seg11:0xb09c]`
- **seg8:0x6afa's party roles are undefined unless the player or a +0x54 object takes part.** Its A/B orientation flag [bp − 0xc] has only four writers, applied in order with the last winning: candidate is the player → 1, caller is the player → 0, candidate byte +0x54 set → 1, caller byte +0x54 set → 0. The prologue does not initialise it, so for two other objects the roles come from the stack slot: only the call that ends a search writes it, so every call of one seg8:0x50aa search reads what lay there when the search began. Do not read a default role into the code; [ADR 0015](../decisions/0015-collision-orientation.md) sets the port's rule ([core.md](core.md#pair-test-seg80x6afa)). `[BYTES seg8:0x6b04 seg8:0x6d0e seg8:0x6d23 seg8:0x6d3d seg8:0x6d57 seg8:0x6d5c]`
- **ISPACE.DLL seg10:0xa184 and seg10:0xa2be are INSPACE.EXE addresses.** In ISPACE.DLL those offsets hold no decoded function; in INSPACE.EXE they are instructions of export 13 (seg10:0xa118), the Restore Game description that ISPACE.DLL reaches through GetProcAddress. Cite them without a module name ([formats.md](formats.md#the-headers-readers)). `[BYTES seg10:0xa184 seg10:0xa2be]` `[BYTES ISPACE.DLL seg10:0x1cdf]`
- **seg16:0xb4e and the push-off read different pool-12 records.** The dispatch's nearest-gate loop reads the even records 2p, the push-off loop of the ambulance mover reads offset k·0xe0 + 0x74, the odd record 2k + 1; read the stride and the offset together before naming a record ([core.md](core.md#the-mover-seg160xa2)). `[BYTES seg16:0xc48 seg16:0x6d0 seg16:0x6d9]`
- **The ship pool is DGROUP:0x9324, not 14.** The credit tests of seg8:0x5df2 compare a pool with the word DGROUP:0x9324 (`mov ax, word ptr [0x9324]; cmp ...`), which is 14 in a wave and 20 in seg18:0x8bc's layout ([structs.md](structs.md#pool-roles)), and seg3:0x6ec gets it pushed from memory. A compare with the literal 14 is wrong in that layout. `[BYTES seg8:0x60c3 seg8:0x60ce seg8:0x6159 seg8:0x6174 seg18:0x973]`
- **A stack byte can hold the directive being decoded.** seg10:0xa332 stores each directive letter in [bp − 0x6a] (seg10:0xa3c9), so its %N test "DGROUP:0x93aa = 11 and [bp − 0x6a] = 0" never holds and %N always writes CR LF ([shell.md](shell.md#game-start-dialogs), Formatter). List a local's writers before reading a branch on it. `[BYTES seg10:0xa3c9 seg10:0xa6ec seg10:0xa6f3]`
- **Subtract the buffer's base from a `[bp + si − k]` index.** With the buffer at [bp − 0x68] and si = lstrlen, `cmp byte ptr [bp + si - 0x6a], 0x5e` tests buf[len − 2], not the last character: %S cuts a trailing caret pair such as ^N, and no ENG_LANG.DLL string ends in a bare '^'. `[BYTES seg10:0xa4d8 seg10:0xa4f5 seg10:0xa4f7 seg10:0xa50b]` `[BYTES ENG_LANG.DLL STRING]`
- **A `push` before seg10:0x6c02 is a graphic id, not a string.** The listing annotates `push 0x168` at seg7:0x255f as the DGROUP string "SmWnd", but seg10:0x6c02's first argument is an IGRAPHIC id: graphic 360, the ice and virus overlay, as `push 0xe6` (230) and `push 0x1f4` (500) are graphics elsewhere. Read the callee's arguments before taking an annotation. `[BYTES seg7:0x255f seg7:0x47c0 seg13:0x5e02]`
- **A routine's only call site is not the only path to its effect.** The tank respawn seg12:0x4f4e has one call, at seg12:0x3ee5 in seg12:0x3e98, which returns at once outside kind-6 waves, but seg12:0x515e also reactivates idle pool-4 tanks, from seg7:0xe78 in kind-7 waves. List the writers of the field (here pool-4 `state` +0x18 = 0 through DGROUP:0x1e08) before concluding that nothing restores an object ([core.md](core.md#the-fuel-tank-pool-4-seg120xae4)). `[BYTES seg12:0x3ea8 seg12:0x3eaf seg12:0x3ee5 seg7:0xe71 seg7:0xe78 seg12:0x5281 seg9:0xf55]`
- **A value latched at entry outlives a later index change.** seg17:0x20fa reads the phase-11 slot from ship word +0x50 of DGROUP:0x9464 at its entry, and the Space call raises DGROUP:0x9464 after that read, so its first growth frame draws the previous ship's slot with the new ship's cell ([shell.md](shell.md#screen-states), Phase 11). Read where a routine latches its locals before tying a draw to the current index. `[BYTES seg17:0x2109 seg17:0x211a seg17:0x228c seg17:0x2563]`
- **The port holds the directory records twice.** `world::DirRecord` keeps the raw 0x297 bytes and `nav::DirRecord` the path, the two counts and the state byte, with no sync between them; a saved file needs the one byte store of [formats.md](formats.md#directory-records-0x297-bytes), so read and write the Navigation fields in the raw bytes. `[DESIGN]`
- **Byte 0x98 in 16-bit code is CBW.** The listings print it as `cwde`, but in a 16-bit segment it sign-extends AL into AX, so a byte read before it is signed: ordinal 32's brightness byte of 240 is −16 and gives scene 105's records 2 and 4 a level of −81. `[BYTES ISPACE.DLL seg8:0x1720 seg8:0x174e-0x1754]`
- **Ordinal 12 is not an average of ramp levels.** A mix of each pixel's ramp level with its neighbours' matches about three quarters of the title emblem's interior and is one level off elsewhere; the picture comes from brightness planes with edge and corner adds, a diagonal blur, a staircase pass and a nearest-brightness walk on the ramp, and each step changes thousands of the emblem's pixels ([ispace.md](ispace.md#ordinal-notes), 12). `[BYTES ISPACE.DLL seg7:0x12d8] [ORACLE probe-0001]`
- **The traced oracle's state-6 timings are not the original's pace.** A relay-traced run writes a negative Calibrate, which starts each screen state at a threshold of 0 and takes every slow-machine branch, and on its host the screen threshold wraps above 511, so whole phases of a visit run a frame per pass: a 16 ms corridor or a 6 ms rise says nothing about the game's design. Compare with the paced stretches of a run and count the Calibrate branches ([timing.md](timing.md#adaptive-screen-threshold)). `[ORACLE core-0007] [ORACLE core-0008]`
- **Not every state-6 routine reads the fast flag.** Ctrl's DGROUP:0x928 is read only by the corridor, the incoming jet and the descent in seg15; the typing, the pad's moves and the launch run their own times with it set. `[BYTES seg15:0x1dab seg15:0x3192 seg15:0x3cb9 seg15:0x3876] [ORACLE core-0007]`
- **A global that looks like the branch flag can be dead.** seg10:0x9a2a stores DGROUP:0x103a = 1 on its reload path, but the pass branches on the local [bp − 0x14] and the global's only reader clears it; list the readers of a flag before taking a write as the switch ([shell.md](shell.md#rescale-seg100x9a2a)). `[BYTES seg10:0x9ab6 seg9:0x274e seg9:0x2755 seg9:0x6992]`
- **A watched counter is seen after the pass's own increment.** The retarget of seg12:0x586 runs at age 13k and the age rises later in the same pass, so a lock appears in a poll at age 13k + 1 (40, 92, 27 and 14 are 13k + 1), not at 13k ([core.md](core.md#the-retarget-seg120x586)). `[BYTES seg12:0xa6-0xab seg12:0x445]`
- **A mask or doubling step does not scale a distance word.** The Size rescale writes pool-8 `extent` +0x20 as the scaled side << 3, but the placement stores it unscaled, so a live rescale and a fresh load disagree at Size 0 and 2; read the template and the rescale separately before assuming one rule ([shell.md](shell.md#rescale-seg100x9a2a)). `[BYTES seg9:0x1c9b-0x1caa seg10:0x9efd-0x9f0c]`

## Tools
- **Ghidra decompilation is only as good as the import.** Without NE relocation records, Ghidra resolves no imports or far calls, and it disassembles DGROUP as code. Import the output of `isre rebuild`, never the packed file. `[REF Ghidra 12.1.2 NE loader]`
- **Linear-sweep disassembly loses sync** inside data embedded in code (for example `seg5:0x351` swallows the prologue at `0x352`). Use `isre asm`, which descends recursively from known entries. `[BYTES seg5:0x351]`
- **rea opens neither NE images nor Ghidra projects** (`unsupported NE executable in MZ image`, also for the rebuilt NE). It opens only a single segment loaded as `dos-com` (base `+0x100`; convert with `isre addr`), which loses relocations, assumes DS = CS and finds few functions. Use the Ghidra pipeline and `isre pack` instead. `[REF rea-agents 6.4.0 open_binary]`
- **`theworks/SETUP.EXE` is not the free game installer.** It is The Works! add-on installer: it takes ISPACE ordinal 24 by GetProcAddress and never calls it. The free installer is the v1.29.07 `SETUP.EXE` of the website's inspace.zip, a comparison build outside `original/` ([install.md](install.md#registration)). `[BYTES theworks/SETUP.EXE DGROUP:0x13c0]` `[BYTES v1.29.07/SETUP.EXE seg2:0x3fda]`
- **Screenshots do not time sub-second events.** The oracle shoots about every 0.55 s, so an interval read from screenshots can be off by half a second (the load screen's 2.0 s read as 2.2 s). Take times from the relay trace's timestamps. `[ORACLE start-0001]`
- **The default relay profile hides some calls.** It excludes USER GetDC, ReleaseDC, SelectPalette and GetCurrentTime, so their absence from a trace proves nothing; test for a call the code always makes on that path, such as RealizePalette. `[ORACLE start-0001]`
- **The oracle's waveOut traffic does not identify sound ids.** With more than one channel WaveMix mixes every effect into its own output buffers, so `waveOutWrite` data and timing say nothing about which id played. Take the id from the ordinal 9 call (a relay of the call into ISPACE.DLL or a breakpoint at ISPACE.DLL seg9:0xc42), or run with `MixChannels=1`, where each play is one `sndPlaySound` ([sound.md](sound.md#playing)). `[BYTES ISPACE.DLL seg9:0x13be seg9:0x1333]` `[DESIGN]`
- **Run whisper-cli once per file.** Given several files in one run, its output does not name the file each line belongs to, so transcripts cannot be matched to resources. `[REF whisper.cpp whisper-cli]`
- **The Hermes-era docs in `../innerspace-rea/` are unreliable.** Their claims marked VERIFIED include errors. Re-derive from bytes before carrying any claim forward. `[DESIGN]`
- **A Win32 edit decides its border at WM_NCCREATE.** The edit control reads `WS_EX_CLIENTEDGE` from the CREATESTRUCT once and places its text as if the 3D edge were there, even after `SetWindowLong` removes the edge, so the text of a Win16-style 1-pixel-border edit lands 1 px up and left. Take the edge off in a CBT hook before WM_NCCREATE (the port's `gfx::Win16EditScope`), not afterwards. [ORACLE m2-accept-0001] [DESIGN]
- **The effect table's first word is a frame counter, not a kind.** Every creator writes 1 there and seg8:0x3fbe raises it once per frame until it reaches word +0x02; the type is word +0x0a ([structs.md](structs.md#effect-table-45--0x14-bytes-at-dgroup0x1e90)). `[BYTES seg16:0x91e seg8:0x4190 seg8:0x419c seg16:0x9f1]`
- **The collision damage words are not reset per collision.** DGROUP:0x9436/0x9438 keep the last bounce's values, and a pool-5 party, which skips ordinal 29, is dispatched with them ([core.md](core.md#response-seg80x546c)). `[BYTES seg8:0x5794 seg8:0x5860 seg8:0x5a96]`
- **seg8:0x698a and seg8:0x6a44 copy the slot velocity unchanged.** Nothing rescales the velocity slots between the bounce and these writers; only the bounce's own separating branch scales them. `[BYTES seg8:0x69c1 seg8:0x69d8 seg8:0x6a7b seg8:0x6a92]` `[BYTES ISPACE.DLL seg2:0x1c0 seg2:0x348]`
