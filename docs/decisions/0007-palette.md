# ADR 0007: Palette

- **Status:** Accepted (the Consequences lines on solid colours and on text on 2026-11-08); the Consequences lines on the checkerboard shadows, the fades, plain RGB greys and palette command 6 (2026-11-09) are Proposed. [DESIGN]
- **Scope:** how the port reproduces the original's 256-colour palette, its animation and fades, on displays that have no hardware palette. [DESIGN]

## Context
- **The original is a palette program.** ISPACE.DLL creates one 256-entry logical palette: entries 0–9 and 246–255 copy the system colours, entries 10–245 are the game's and are animated with `AnimatePalette(hpal, 10, 236, …)`, the only such call in either module ([shell.md](../re/shell.md#palette)). [BYTES ISPACE.DLL seg5:0x3596] [BYTES ISPACE.DLL seg5:0x441a] [ORACLE depth8-0002]
- **Pixels are indices.** Every 8-bit image becomes a device bitmap through `CreateDIBitmap` with `DIB_PAL_COLORS` and the indices 0–255, so a pixel value is an index into the game palette, and a change of the palette recolours every image at once. Colour schemes, colour allocation (commands 6 and 7) and the intro fades (ordinal 14) all work by rewriting entries and animating ([shell.md](../re/shell.md#palette)). [BYTES ISPACE.DLL seg5:0x2080] [BYTES ISPACE.DLL seg5:0x50cc]
- **At 8 bits per pixel the game chooses `PALETTEINDEX` colours and at higher depths `PALETTERGB`,** and the title asks for "256 color mode" unless the depth is exactly 8. The manual recommends 256 colours ([shell.md](../re/shell.md#window-geometry)). [BYTES ISPACE.DLL seg8:0x27f0] [BYTES seg15:0x71e8] [MANUAL Ship Factory]
- **At depth 24 under Wine the title, briefing bars, sprite, radar dots and dim HUD text lose their colours,** because `AnimatePalette` changes nothing on a true-colour display. On Windows 10 and 11 every display is true colour, and `WM_QUERYNEWPALETTE` and `WM_PALETTECHANGED` never arrive. [ORACLE depth8-0002] [REF Win32 SDK, Palettes]
- **`UpdateColors`** is called once, on the palette-changed path. It has no true-colour equivalent. [BYTES seg2:0x5a2]

## Decision
1. **The port behaves as a 256-colour display.** It keeps one 256-entry software palette with the original's layout: entries 0–9 and 246–255 hold the 20 static colours of the Windows VGA palette, entries 10–245 are the game's and start black with `PC_RESERVED` semantics. [DESIGN]
2. **Drawing goes into an 8-bit DIB section** at the logical size (ADR 0006), through the same GDI calls the original makes (`BitBlt`, `StretchBlt`, `PatBlt`, text), with the game's images as 8-bit DIB sections whose pixels are indices. The colour table of the drawing surface is the palette's indices (`DIB_PAL_COLORS`), so colours written as `PALETTEINDEX(n)` land as `n`. [DESIGN]
3. **Presentation converts indices to colours** once per frame with the current palette as a 256-entry lookup table into a 32-bit surface, which ADR 0006 scales to the window. `AnimatePalette`, the schemes, allocation and fades become writes to the table and cost nothing else. [DESIGN]
4. **The palette manager is ported as it is:** ordinal 4's commands 0–8 and ordinal 14, with their entry ranges, slot tables and the RGB order of ISPACE.DLL #5500 100, from [shell.md](../re/shell.md#palette). Command 0 reads the port's fixed device answers: `BITSPIXEL` 8, `SIZEPALETTE` 256, `NUMRESERVED` 20. [DESIGN]
5. **Palette messages are emulated, not received.** A 256-colour Windows sends `WM_QUERYNEWPALETTE` to the main window at every activation, and while the game holds a palette (DGROUP:0x920e ≠ 0) the original's handler realises it, erases the client area to black with the class brush and repaints, which in most states draws nothing until the next frame ([shell.md](../re/shell.md#palette)). The Wine oracle at 32 bpp delivers the message after every dialog, so the screen goes black around Restore Game and New Game; whether Windows 10 and 11 deliver it at true colour is [OPEN]. The port's display has no palette and the NT model sends `WM_QUERYNEWPALETTE` only on palette displays, so the port runs nothing on an activation: it ignores `WM_QUERYNEWPALETTE` and `WM_PALETTECHANGED` from Win32 and does not emulate the handler's erase and repaint. The real Windows 98 machine, whose display has no palette either, keeps the status display across the wave start's reactivation ([win98-0001](../../oracle/digests/win98-0001.md)); the Wine oracle's blackouts around the dialogs and at the wave start are Wine's message, not the target's. It never calls `RealizePalette` or `UpdateColors`; `WM_PALETTECHANGED` changes no pixels in the 8-bit model. The title never shows the "256 color mode" hint. A host on a 256-colour display would need the handler's sequence (`src/gfx/palette_message.*` holds it, unused). [DESIGN] [BYTES seg2:0x5cb seg2:0x56d seg2:0x7ac] [ORACLE start-0001] [ORACLE win98-0001] [REF ReactOS win32ss/user/ntuser/focus.c]
6. **Dialogs and menus** are Win32 controls and keep the system's true-colour drawing, as they did on an 8-bit display with the static colours. [DESIGN]

## Alternatives
- **Converting the images to 32-bit at load:** loses palette animation, schemes, fades and colour allocation, all of which the original does every frame or on every scene change. Rejected. [DESIGN]
- **Emulating the depth-24 path (`PALETTERGB`):** reproduces the colour losses the oracle saw at depth 24, which were never the intended look. Rejected. [DESIGN]
- **GDI's own 8-bit DIB section without a presentation step:** Windows converts it with the DIB's colour table at blit time, so animating the palette would mean rewriting the colour table through `SetDIBColorTable` each frame, which is the same lookup in another form but offers no control over scaling. Possible fallback. [DESIGN]

## Consequences
- M2 ports the palette manager into `src/gfx/palette` with tests that pin every command's entry ranges against shell.md. [DESIGN]
- **The presenter is one isolated step** (index surface + palette + window in, pixels on screen out), implemented with GDI (a 32-bit DIB section and `StretchBlt`). A Direct3D or OpenGL presenter can be added later for vsync or borderless full screen without touching the palette or the surface code. GDI stays the only renderer until a need is measured. [DESIGN]
- The sprite readers of M1 (`src/formats/dib`) already give 8-bit pixels and the 256-colour tables the lookup needs. [DESIGN]
- Checklist rows SYS-24, SYS-25, WIN-04 and WIN-55 describe the behaviour this ADR replaces or ports. [DESIGN]
- **Solid colours and own-colour-table graphics land on the nearest palette entry.** A solid colour (a brush, a pen or a text colour) and a 4-bpp graphic that ordinal 1 loads with its own colour table (d = 3 with a = b = 12 writes no palette entry and the bitmap is built with DIB_RGB_COLORS, [ispace.md](../re/ispace.md#ordinal-notes)) show the nearest entry of the realised wave palette on the port's 256-colour display, as on a 256-colour Windows display, where the 24-bpp oracle shows the exact RGB. So the fuel can (IGRAPHIC #4000 270) shows #CD3300 for #D31919, #AF2B00 for #B51414, #9B2600 for #9E2203, #872100 for #8D1305, #642828 for #761B1B and #FF0000 for #ED0C0C; the EXIT picture (#4000 500) #FF5600 for #FF5A00 and #AF2B00 for #BE0000; and the damage lamps (#FFC400 and #FF6100 for #FFC000 and #FF6000), the score digits, the shot dots and the gate beam likewise. These are the port's design under decisions 1 and 2, not a wrong colour table, and the oracle comparison of such pixels takes the nearest entry of the scheme's palette, not the oracle's RGB. [BYTES IGRAPHIC.DLL 4000 270] [BYTES IGRAPHIC.DLL 4000 500] [BYTES ISPACE.DLL 5500 100] [BYTES ISPACE.DLL seg5:0x2bec-0x2bff seg5:0x34b1] [DESIGN]
- **Text on the 8-bit surface is drawn with `ExtTextOut` and the advances of its extent** (`GetTextExtentExPoint`), so the glyphs sit where a true-colour GDI places them. Wine steps monochrome glyphs by their hinted cells, which made the debriefing title's ink 150 px wide on the 8-bit surface where the oracle's is 158 px; on Windows GDI keeps the two in step and nothing changes. The glyphs are not smoothed, as on a 256-colour display. [DESIGN]
- **The checkerboard shadows are drawn (Proposed, 2026-11-09).** At depth ≤ 8 the bytes draw a shadow of the ship with ROP 0x00A803A9, D AND (P OR S), from the frame's mask through the brush DGROUP:0x5eaa, the AA/55 checkerboard (DGROUP:0x5ea8 below 8 bpp), which blacks every other pixel of the ship's silhouette, offset below it, on what lies there: the incoming jet seg15:0x3caa, the descent seg15:0x374c, the pad strip of seg15:0x4c76 and the rise seg15:0x0 ([shell.md](../re/shell.md#the-landing-scene), [core.md](../re/core.md#the-descent-seg150x374c)). The port is a 256-colour display (decision 1), so it draws them. The 24-bpp oracle skips every one of these blits, so the oracle comparisons exclude the shadows' pixels. [BYTES seg15:0x4050-0x40c4 seg15:0x3a94-0x3b12 seg15:0x4e24-0x4f67 seg15:0x3d9-0x4d1] [DESIGN]
- **The palette fades show (Proposed, 2026-11-09).** ISPACE.DLL ordinal 14's fades animate palette entries, so on the port's 256-colour display the rising pad ship and the incoming jet's top view darken by a colour ratio of 1.07 to 1.39 while their shapes stay the same; the 24-bpp oracle, whose bitmaps hold RGB, shows no fade. The comparison of those frames checks shapes and counts the colour ratio separately. [ORACLE core-0007] [ORACLE core-0008] [DESIGN]
- **Plain RGB greys take the nearest static colour (Proposed, 2026-11-09).** ISPACE.DLL ordinal 35 draws the visit's bar boxes with DKGRAY, RGB(64, 64, 64), a plain RGB that lands on the nearest static colour under decisions 1 and 2; black and #808080 are equally far and the tie goes to the lower index, so the port's line is black where the oracle shows #404040 (975 px per visit). This follows the solid-colour line above and is not a wrong colour table. [ORACLE core-0007] [DESIGN]
- **The desk pad's and the scene renderer's colours come from palette command 6 (Proposed, 2026-11-09).** The pad drawer seg15:0x482e and ISPACE.DLL ordinal 32 allocate their greys and shades through palette command 6, and the port's ordinal 32 takes seg8:0x27f0's PALETTERGB branch, as a display above 8 bpp would, rather than the 8-bpp PALETTEINDEX ramp branch, so its colours are realised as nearest entries. The pixel comparisons against core-0007 and core-0008 hold at 0 px outside the greys within 3 levels. Porting the 8-bpp branch is a later fidelity pass (M10). [BYTES ISPACE.DLL seg8:0x27f0 seg8:0x14ac] [BYTES seg15:0x482e] [DESIGN]
